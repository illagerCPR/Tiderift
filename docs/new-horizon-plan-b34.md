## 二、已确认的接入点和共同约束

- `src/items/ItemDefs.js` 已注册 `map`，但未查到地图使用链或合成配方。A 首版从游记界面入口进入，地图物品接线可同轮评估，但不可让生存玩家因缺配方而无法使用核心功能。
- `src/ui/SteleScreen.js` 已能按 `StructureManager.steleChapterAt()` 读取章节；发现记录须由真实世界交互触发，命令面板指定章节或调试调用不得误算为探索。
- `src/world/structures/aetherStructures.js` 的 `solveTower()` 已生成带荧石灯的瞭望塔。B 的“修复”应表现为旧航标重新激活，不能将现有荧石描述成完全熄灭；塔锚点从确定性结构记录取得，不改变既有塔的选址、密度或生成随机流。
- `src/player/GlideWind.js` 已实现鞘翅与气流，C 复用现有物理。计时和检查点逻辑独立于气动参数。
- 单机状态进入 `SaveSystem`，联机房间共享状态由服务器校验、落盘和回放；个人探索及个人成绩按玩家档案或独立个人记录保存。`NetworkManager` 现有 `profile_save` 每 15 秒发送，扩字段前须核对体积、清洗与重连顺序，不可把无限增长的数据塞进高频 `player_state`。
- 新增方块/状态变体只能追加在 `BlockDefs.js` 尾部；新增物品与 SVG、显示名、多语言同步。所有世界方块改动走 `World.setBlock`；客户端重建世界时，UI、监听器、粒子和纹理要随生命周期释放。
- 联机数据键至少包含房间、维度、坐标；涉及个人记录时再包含稳定的当前昵称身份。换房、换维、重连与服务器重启后，不得把旧房间、旧维度的数据混入当前世界。服务端对坐标、数量、文本和数据结构设置边界。

## 三、A：四界游记与手绘地图

**玩家流程**：进入某维度 → 行走揭开周围地图 → 接近并实际发现遗迹 → 读碑后可在游记中回看 → 放个人标记，联机时可选择分享为房间标记。未到过的区域不显示地形、结构或目标位置。

1. **数据模型**：以维度分桶保存已探索的区块格、已发现的结构实例键、已读章节 id、个人标记；房间共享标记单独入房间账本。区块格按区域压缩或等效稀疏格式存储，标记和文本有数量、长度上限。旧单机存档缺字段时回落为空游记，旧联机档案缺字段时同样回落为空；存档版本变更只在确需迁移时进行。
2. **揭图规则**：只由玩家当前位置跨入新格触发，四维分别计算。地图画面用已揭格的确定性群系色与简单地形纹样，不为未揭格批量调用结构求解；打开、缩放和拖动地图不得生成区块或造成明显单帧尖峰。探索记录归玩家，地图 UI 可查看其他维度已经探索的部分。
3. **发现与阅读**：发现结构必须来自玩家抵达时的附近结构记录，并记录唯一的“维度 + 类型 + 锚点”；重复进入幂等。碑文回看记录有效章节 id，标题和正文仍从现有 `STELE_CHAPTERS` 获取，不把十余种翻译正文写进存档。若结构原件被破坏，历史发现与已读章节仍保留。
4. **标记与联机**：个人标记仅本人可见；“分享”是一次明确操作，服务器清洗并保存房间标记，再向同房间玩家广播。共享标记可被其他人看到，但不替他们揭开地图；删除权限、冲突规则和房间重建后的清理规则在协议中明确。非房主修改不得覆盖整份账本。
5. **界面**：单一游记入口含四维地图、当前维度、标记列表、已读碑文。新界面遵循 E/ESC、`controls.enabled`、世界输入门控及 `start()`/`_disposeWorld()` 生命周期约定。界面文本接入现有 11 语言包，用户标记文本安全显示。

**A 验收**：同种子不同探索路径只揭开实际到达格；未发现的塔/要塞不出现在图上；跨维度、存档重开、区块卸载和联机重连后记录一致；双端共享标记可见且私有揭图不外泄；服务端重启后共享标记仍在；大量已揭格时打开地图和自动保存不出现明显卡顿。补覆盖数据清洗、幂等、存档往返与房间隔离的确定性用例，再用浏览器实走、读碑与双会话共享核对画面。

## 四、B：旧航路修复

**玩家流程**：从游记中找到已发现的天域瞭望塔 → 在塔顶检查旧航标 → 分三阶段提交材料并修复 → 看到明确的激活反馈与下一处航路方向 → 再到下一座岛。多人可以分头收集材料，进度以房间状态为准。

1. **塔身份**：只对既有 `aether_tower` 结构开放，键为“天域 + 结构类型 + 确定性锚点”。修复入口限定塔顶具体交互位置并验证结构存在，不能把玩家自建的普通荧石塔识别为旧航路。既有塔选址与几何保持稳定；若塔关键部件被玩家破坏，界面提示缺件并要求修复或允许恢复后继续。
2. **三阶段**：定义可获取的材料配方和明确消耗顺序；每阶段只接受一次有效提交，重复点击、断线重发或两人同时提交不得双重扣料、跳级或重复奖励。必要的方块变化走 `World.setBlock`；进度单机随存档、联机由服务器权威记录并向房间广播。
3. **激活反馈**：区分原有荧石照明与修好的航标，可用新纹样、光效、音效及游记状态共同表达。反馈随距离与可见性节流，离开/返回、换维和重连后从状态重建；不永久堆积 Three 资源或渲染特效。
4. **导航**：首版指向同一维度一处确定存在的候选塔，算法只依赖种子与锚点，限半径/搜索预算并避开当前塔；找不到时给出清楚提示，不伪造目标。未抵达的下一塔只显示方向与大致距离，仍不在 A 的探索地图上提前揭出精确遗迹位置。被修好的塔在 A 的游记中显示为已修复。
5. **奖励**：首版以航路记录、铭牌或装饰与导航便利为主；若新增物品或方块，注册、纹理、配方、掉落、背包图标及 11 语言一并补齐，不改变终局纹章的门控。

**B 验收**：同种子双端识别同一塔并得到相同目标；既有世界的塔位置/箱子/碑文不漂移；三阶段在并发提交、掉线重发和服务端重启后保持一次性语义；新玩家入房与跨维返回后看到一致进度；拆改塔顶后不会出现幽灵航标。浏览器完成一次从发现到修复再沿指引抵达下一岛的流程。

## 五、C：御风竞速与自建赛道

**玩家流程**：放置起终点和顺序检查点 → 为赛道命名并保存 → 从起点出发，按顺序穿过检查点 → 在终点看到本次用时和个人最佳。联机玩家可挑战同一条房间赛道，各人分别记录成绩。

1. **赛道定义**：同一维度内一处起点、一处终点、至少一个且至多有限个有序检查点；用少量可识别的方块或设置界面创建，方块注册遵循尾部追加。赛道有稳定 id 与修订号，名称、点位范围、赛道数量和每条长度受服务端限制；跨维点位与重叠/无效定义被拒绝。
2. **存储与编辑**：单机赛道与成绩进存档；联机赛道定义归房间账本，创建者或房间管理者可编辑/删除，更新向所有同房间玩家同步。编辑赛道使旧成绩与旧修订号分离，重启服务、晚加入和断线重连都能恢复定义。方块被挖掉时要处理赛道失效及编辑提示，不能静默保留不可完成的跑道。
3. **计时规则**：必须从起点主动开始，依序进入检查点的判定区域，只计同一维度玩家的实际移动；乱序和重复穿过无效。使用单调时钟计时，暂停、死亡、换维、换房、断线或赛道被编辑时取消本次尝试，避免后台标签页得到异常成绩。创造飞行/终局纹章飞行与鞘翅赛道分别标识或限制，成绩界面不可混为同一榜。
4. **成绩语义**：首版仅个人最佳和朋友间娱乐，联机成绩记录的接收、清洗与持久化由服务端处理；界面不宣称服务器已验证真实运动轨迹。公开排行榜、幽灵回放与防作弊验证留待后续单独评审。
5. **体验接线**：赛道开始与终点显示简洁计时 HUD，检查点有清楚的三维反馈；赛道可在 A 的游记中作为用户创建的标记管理。复用现有鞘翅、气流和云绒块，不改滑翔气动与世界生成。

**C 验收**：顺序、乱序、折返、重复触碰、重置和无效赛道行为明确；单机重开及联机新加入/重连/重启后赛道与有效成绩仍在；编辑后旧成绩不充当新赛道纪录；两名玩家能同时跑同一赛道而互不覆盖；暂停、死亡、换维和断线取消计时。浏览器实际飞行一条最短赛道并核对 HUD、记录与另一端可见性。

## 六、每轮验收与收尾

1. 实施时先记录该轮旧行为与设计中的数据格式，再修改代码。新增自动化用例只覆盖真实风险，按需接入唯一 runner；所有修改的 JS/MJS 文件执行 `node --check`。
2. 运行对应聚焦用例、`npm run build` 与 `npm test`；按 `AGENTS.md` 使用浏览器实际手测 UI、指针锁移动与联机流程，记录使用的种子、房间和维度。测试用一次性房间，检查结束后按既有跑批清理流程收尾。
3. 记录数据兼容、性能和未覆盖边界，更新 `docs/TODO.md` 与相应 `docs/agent-notes/`，再进行该轮唯一提交、推送、CI 观察。CI 通过后核对远端提交哈希；A/B 到此停下，C 继续完成 Build 34 发布与说明。
4. C 发布前核对 `src/version.js` 为 34、tag 指向已绿的 C 提交、发布说明覆盖 A/B/C。Build 34 的三个里程碑全部完成后，才把 `Idea-WV1-New-Horizon` 的 A/B/C 在 TODO 中标为已交付；D–G 保留候选。
